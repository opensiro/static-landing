What the target includes

Illustrative 100 selected tasks × 10,000 total tokens per task = 1,000,000 tokens. The per-task allowance includes all input, output, tool-context tokens, and retries within that evaluation. Additional seeds or trials must be added to the budget.

Task generation, generator calibration, failed setup, sandbox compute, and later full evaluations are separate costs. No measured task throughput, production invoice, or guaranteed predictive accuracy is available for OpenSiro yet.

From a taxonomy leaf to a validated generator
Calibration plan
  1. Define the capability leaf and its failure modes.
  2. Generate candidate tasks with controllable difficulty.
  3. Run diverse harness versions on a fixed model.
  4. Measure task sensitivity and correlation with held-out full-benchmark outcomes.
  5. Check ranking stability, false positives, false negatives, and seed variance.
  6. Accept the generator only if it retains useful signal on unseen harness changes.

Evo-Bench §4.2 motivates sensitivity-aware selection; it does not validate OpenSiro’s generators. Keep generator calibration and final validation data separate.

Token totals across different models are bookkeeping, not equivalent compute. Do not turn a token ratio into a dollar ratio without separate input, output, cached-token, and infrastructure accounting.

Validation metrics and how to report them
Spearman correlation
Agreement between proxy and full-benchmark harness rankings. Report score and delta correlations separately, with uncertainty. Ranking precedent ↗
Pairwise ranking accuracy
Fraction of harness pairs ordered consistently. Pre-register tie handling; report tied pairs separately. PACE protocol ↗
Positive-delta precision
TP / (TP + FP): among improvements predicted by the proxy, how often does the full benchmark improve? Set a minimum meaningful delta before evaluation. Precision methodology ↗
Top-K recall
Number of full-benchmark top-K harnesses kept by proxy screening, divided by K. Report K and shortlist size. OpenSiro’s proposed retrieval-style use of recall ↗.
False positives / negatives
FP: proxy improves, full result does not. FN: proxy misses a full-benchmark improvement. Report FPR = FP / (FP + TN) and FNR = FN / (FN + TP); these denominators differ from precision. Confusion matrix ↗
Evaluation cost reduction
Full-evaluation cost / proxy-evaluation cost, using the same currency and accounting boundaries. Also report end-to-end screening cost including calibration, finalists, retries, generation, and sandbox compute. Cost model ↓

Use paired tasks and seeds where possible, hold out harness changes and generated task families, and bootstrap at the level of independent units. Report confidence / bootstrap intervals, seed sensitivity, and a power analysis; a small number of harness variants can yield unstable correlations. Interval-estimation precedent: Deep RL at the Edge of the Statistical Precipice ↗

These are proposed OpenSiro measurements. A denominator with no eligible pairs, positives, or finalists is undefined and must be reported as such. No correlation or reliability target on this page is an observed OpenSiro result.

Threats to validity
  • Proxy overfitting
  • Taxonomy incompleteness
  • Distribution shift
  • Model-specific harness effects
  • Benchmark contamination
  • Random seed variance
  • Stochastic tool execution
  • Hidden state and environment differences
  • False confidence from small samples
  • Changing provider prices
  • Cached-token accounting
  • API versus self-hosted inference

Keep the model, tokenizer, runtime, tool versions, and environment explicit. An improvement on a small model does not establish the same gain on a frontier model.

Self-hosted inference: infrastructure and engineering are separate costs

API inference

Provider token categories × their prices, plus tool and service charges.

Self-hosted GPU

GPU count × hourly rate × billed duration, plus CPU, storage, and sandbox costs.

Amortized engineering

Setup, maintenance, and calibration effort allocated across the development runs they support.

GPU count × GPU hourly price × evaluation hours
÷ total evaluated tokens = infrastructure cost per token

Infrastructure estimate Example assumptions: one NVIDIA A10G, Qwen2.5-7B-Instruct with 4-bit weights, 8K context cap, batch size 1, concurrency 1, and an assumed $1/GPU-hour. None are an observed OpenSiro deployment or a current GPU quote.

Assume 800K input tokens at 2,000 input tokens/s and 200K output tokens at 100 output tokens/s, with 50% effective utilization across the elapsed run. Duration ≈ (800,000 / 2,000 + 200,000 / 100) / 0.5 = 4,800 seconds = 1.333 hours. GPU-only cost ≈ $1.33, or $1.33 per million total tokens. All throughput and utilization values are illustrative assumptions; tool wait time is absorbed into that utilization assumption.

This is an infrastructure estimate, not an API invoice. It excludes cold starts, extra billed idle time, CPU, storage, and engineering. A longer context, quantization, batching, and tool waits can change latency and total cost; tokens alone do not determine trajectory cost.

Replace assumptions with measurements from vLLM’s serving benchmark and rates from Hugging Face Inference Endpoints pricing or the selected host. Record model revision, quantization, GPU, batch size, concurrency, input/output lengths, latency, throughput, and utilization. PagedAttention’s experiments explain why serving configuration matters.
